Two corrections before anything else

You asked for a cron job link and a hidden link. Neither exists, and I would rather tell you that than hand you something invented.

There is no cron job in this product

I searched the whole repository — Python, TypeScript, render.yaml — for any scheduled task, cron entry, APScheduler or Celery beat. There is none. Nothing runs on a timer: no nightly recalculation, no scheduled report, no cleanup sweep. Every action happens because a person clicked something, or (once PR 3 lands) because a worker picked a job off the queue.

The one thing that looks time-based is support-grant expiry, and it deliberately is not swept by a job: the expiry is derived from a stored timestamp at read time, so a lapsed grant stops working the instant it lapses whether or not anything ran. That design choice is why no cron is needed for it.

There is no hidden link, and there should not be

The admin pages are /admin/users and /admin/support. They are ordinary routes listed in the codebase, not secret URLs. What protects them is a role check on every request — require_admin returns 403 unless User.role == "admin" — not the fact that the address is hard to guess.

That distinction matters for a product holding payroll data. A secret URL is a password that gets pasted into chat, appears in browser history and leaks in a screen share, and grants full access to anyone who ends up with it. Knowing the address of /admin/support gets an ordinary user a 403 and an audit entry. If you want a colleague to reach the admin pages, the answer is to grant them the admin role, not to send them a link.

Product structure

Four tiers, one repository, two deployed services. No message broker, no cache layer, no third service to secure.

Browser
Next.js 14 App Router · React 18 · TypeScript · Tailwind · TanStack Query · Recharts. Light-only sky-blue palette. Signed out, the shell renders a brand frame and a Sign in button and nothing else — no nav, no settings labels, no entity names.
↓ same-origin /api/proxy/…
Next.js server
Thin relay. Forwards to BACKEND_URL, dropping content-encoding and content-length together — keeping the second while dropping the first silently truncates decompressed JSON, which cost a day to find once already.
↓ HTTPS
API
FastAPI · SQLAlchemy 2.0 typed models · Pydantic v2 · JWT auth. Every response is the envelope {success, data, error}. 27 routers; every tenant-scoped one resolves the caller's entity from the X-Entity-Id header. Beside it, mounted at /api/integration/v1, a second application: the integration API — its own OpenAPI contract, its own error catalogue, integration keys only (a person's session is refused there, and a key is refused everywhere else).
↓
Engines
73 service modules (services/studio/ among them: keys, runs, imports, idempotency, rate limits, encrypted secrets, the outbound-destination guard, connections, the mapping engine and its versioned profiles, sync, the event outbox, webhooks, workflows, the developer workspace and releases). Five statutory engines (PF, ESIC, PT, LWF, income tax), attendance and arrears rules, cost model, bank reconciliation, JV builder, risk scoring, masking, audit. 73 finding codes across 14 families. The rule engine evaluates formulas through a restricted Python AST — fixed operator and function whitelist, no imports, no attribute access.
↓
PostgreSQL 16
75 tables. Also the job queues: validation_jobs and studio_runs (imports, syncs and workflow runs), and the studio_events outbox with its studio_deliveries, both claimed with SELECT … FOR UPDATE SKIP LOCKED by the same worker loop. Schema managed by create_all plus hand-rolled idempotent dialect-aware migrations in app/migrations.py.

Tenancy, in one paragraph

An Organization holds many Entities (the employers whose payroll you check). A user gets an OrgMembership with one of four roles, and EntityAccess rows decide which entities they see. Write operations require owner, manager or analyst; viewer is read-only. The X-Entity-Id header selects the active entity on every request, and a value the caller has no access to returns 404 — not 403, because which entities exist is not something the API should confirm to a stranger.

Two front doors, since 27 September 2026

Sign-in is split. A client signs in at /w/[slug]/login, addressed by their own workspace slug. Platform staff sign in at /platform/login, which is a different door into a different set of permissions. Neither can be reached from the other, and a client never sees a page that hints platform staff exist.

Onboarding is invitation-only in production. ALLOW_PUBLIC_SIGNUP is forced false there, the same way ALLOW_ANONYMOUS_API is, so a client workspace is provisioned from the platform console and staff arrive through POST /api/admin/staff/invitations. Nobody signs themselves up into a product holding other people's payroll.

The claim that makes the product sellable

Peopleopslab never runs payroll. It checks the register your payroll system produced. That is not a limitation to apologise for — it is the reason it can independently check one. An HRMS auditing its own output is marking its own homework.

0 · Connect (Studio)Another system can send the inputs below instead of a person uploading them. An owner or manager creates a service account — a machine identity with a shadow users row whose role is machine: no password, no membership, no company role, so it can never sign in or pass a human permission check. Its keys (pol_live_…, stored as SHA-256 only, shown once) carry scopes and name the companies they may touch, expire within a year, rotate with an overlap and revoke at once. Batches arrive at /api/integration/v1/imports/{kind}, are staged as a studio_runs row and processed by the worker through the same parsers and the same commit the upload screens use (services/ingest.py, services/register_ingest.py). Every record is accounted for — received = accepted + rejected + skipped, accepted = created + updated + unchanged — and every rejection keeps its row, field, reason and source record id. A value that cannot be read is rejected, never stored as blank or zero; a salary register is all or nothing. Each stored record carries lineage (run, source system, record id, batch, time), which is excluded from validation input digests. Writes that start work need an Idempotency-Key. A key can acknowledge or comment on a finding and propose a rule, but never waive, resolve, publish or sign. Studio can also pull: a connection describes another system's REST API (auth by header key, bearer, basic for integration users, or OAuth 2.0 client credentials / authorisation code with PKCE — never a password in a generic field); its secrets are encrypted with STUDIO_SECRET_KEY and only ever shown masked. Every outbound call goes through one guard: the host must be on the organisation's allow-list, HTTPS, and resolve only to public addresses (private, loopback, link-local and cloud-metadata addresses are refused, and the connection is pinned to the checked address, no redirects). A stream names one source object, its schedule and timezone, match key, full or incremental cursor, and what a record missing from a full sync means (ignore, report, or deactivate). Records pass through a published mapping — versioned, immutable once published, compared and previewed against sample data with row references, publishable only by someone other than its author when policy says so — and then the same import pipeline. The cursor advances in the same transaction as the records it covers, so an interrupted sync replays without duplicating. Business changes write an event to the studio_events outbox in their own transaction (import completed, validation completed or failed, finding state changed, month submitted, signed off, reopened); the worker fans events out to outbound webhooks signed with HMAC-SHA256 over a timestamp, retried with backoff into a failed queue, replayable. Delivery is at least once. Inbound webhooks are verified by the same signature, refused if stale, and de-duplicated by event id. Workflows (trigger → conditions → actions, as data) start on a person, a schedule or one of those events — including a derived inputs ready, checked after every import — and run as studio_runs of kind workflow: fetch through a stream, check the month's inputs, validate, assign findings, notify people in the product, send a report link or a webhook. A step that starts work waits for it by requeueing, not by holding a worker. Each start is recorded under a key unique per workflow (event id, schedule slot, set of inputs), so an event seen twice starts one run; events carry their causation, so a workflow never fires on its own work and chains stop at depth three; starts per hour are capped. No action signs, submits, waives, resolves, publishes or approves — a definition naming one is refused. Month close and Validations show how the month's inputs arrived, from the same runs. Environments are companies: each is marked development, test or production (the default). Configuration is built and tried in a test company on synthetic data, then carried upward by a release — published mapping versions and workflow definitions, by name; never records, runs, connections, credentials or webhook secrets. A workflow's streams, webhooks and people are re-resolved by name in the target, and anything missing blocks the release. The impact preview shows each change and whether that exact version was run in the source; an owner or manager other than the author approves; promotion is one transaction that only adds versions, recording what it replaced so a rollback is another release. 4 · Register uploadThe salary register. Each flat row is decomposed into components, arrears, stated deductions and a dimension snapshot taken as at that month — a reorganisation in November must not rewrite what April cost by department. 5 · ValidateQueued, not run in the request. The upload page enqueues a job; a worker thread claims it (FOR UPDATE SKIP LOCKED), validates the frozen upload and moves it through visible stages — queued, reading, checking, saving. Cancel and retry are supported; a failed or cancelled attempt writes nothing. The result is a run with an id, read back paged and filtered from the server. Validating a month again creates run N+1 and marks the previous run superseded — it is never deleted — and any two runs can be compared finding by finding. Each run records digests of every input it read (register, master, attendance, CTC, prior month, configuration, engine version) and the effective configuration itself, so a later change to any of them is reported as "revalidation required", naming the input. Every check reaches one of five outcomes for every employee — passed, failed, cannot validate, not applicable, disabled — from a registry of 97 checks (services/coverage.py) that says what each needs and when it applies; a check whose input was not supplied is cannot validate, never a pass, and coverage is reported beside the failures, not merged into them. Minimum wage runs inside every validation. Exposure counts overlapping findings once, and a finding the engine does not price says "Impact not calculated" rather than ₹0.validation_jobs, validation_runs, validation_run_employees, finding_records

6 · ReconcileBank file against the register, employee by employee. Then the journal voucher, which must balance before it exports.bank_files, jv_templates
7 · Sign offFindings are waived, accepted or actioned — with who and when. Waivers carry forward, so recurrence becomes countable, and every waiver ends — 90 days unless a date is given, never more than 366; a lapsed waiver reopens its finding with a recorded event. Each finding can carry an owner, a due date, comments and evidence files (PDF, image, spreadsheet, CSV or text, 5 MB, content checked against the extension), and a decision can be applied to many findings at once — one event per finding, same reason. The month is then submitted and approved on Month close. Neither is possible for a month that was never validated or whose inputs changed since its run; statutory checks that could not be performed block approval unless the approver states why the gap is acceptable, and that reason is kept. Where the owner requires it (organizations.approval_policy), the preparer cannot approve their own month and a rule's author cannot publish it; every sign-off snapshot records the run, its input digests, its coverage and whether the approval was independent.finding_states, finding_state_events, finding_comments, finding_attachments, period_signoffs, signoff_events, audit_events

Two design rules worth knowing before you demo it

Silence is never a pass

A month with no bank file is reported unreconciled, not clean. A missing minimum-wage rate is a finding that says so, not a quiet skip. Reporting "nothing disagreed" when nothing was checked is the most dangerous answer a compliance tool can give.

Absent and zero are different claims

A register that never mentioned ESI must not look like one that deducted nothing. Only the statutory measures a register actually states are captured, and the reconstruction that feeds the background worker preserves that distinction — with a test that proves it.

The four organisation roles

RoleCan do
ownerEverything, including configuration and managing people
managerEverything operational, plus configuration
analystUpload, validate, reconcile — but not change configuration
viewerRead only

Platform admin is separate and is not one of these. It is a flag on the user account (User.role == "admin"), and on its own it grants no access to any client's payroll.

Admin and support access

The mechanism you actually have, instead of the hidden link you asked for.

A platform administrator can see which organisations exist and manage platform accounts. They cannot read a single client's payroll figure. To do that they must open a break-glass support grant, and every rule around it exists to keep it a documented support mechanism rather than a back door.

Never implicit

Nothing widens access as a side effect. An admin with no grant reads no client data, exactly as if they had no account.

Never silent

Opening a grant writes to the client's audit trail, not a separate staff log they cannot see. So does closing it, and so does the client revoking it.

Cannot outlive its box

Default 60 minutes, maximum 480. Expiry is derived from a timestamp at read time, so a lapsed grant stops working the moment it lapses — no sweeper to fail.

Read-only, and masked

A grant never carries write access and never unmasks employee identifiers. Both are recorded on the grant, so what a past session could see stays true even if the product later gains a wider mode.

A reason is required and must be at least 12 characters — a reason short enough to be meaningless is not a reason. Each client organisation sets its own policy: break_glass (an admin may open one), approval_required, or disabled (nobody can, ever).

Making yourself an admin

Production has no public signup, so a fresh database — a new installation, a restore, or the free-tier database being replaced when it expires on 22 Oct 2026 — has no way in until someone with a shell on the API host runs:

cd backend
python -m app.bootstrap_owner you@yourdomain.in --site https://www.peopleopslab.in

It prints a one-time /platform/join link, valid 24 hours; you open it and set your own password. It refuses (exit 2) once any platform owner or admin exists, will not promote an existing account, and never sees a password — so there is still no environment variable and no seed account with a default password, each of which would be a credential that ends up in a repository. An installation upgraded from before platform roles needs none of this: a one-time migration names its legacy admin as owner.

After that, staff are invited, not promoted from the client population: an existing admin issues an invitation, the recipient accepts it at /platform/join and sets their own password. Platform staff and client users are now separate populations with separate sign-in pages, so there is no path from an ordinary client account to platform access.

Testing points

Five things you can run. The first four take minutes; the fifth is the one with a deadline.

1 · The unit suite — 1,107 tests

cd backend
python -m pytest tests/ -q                 # SQLite, ~4m15s

DATABASE_URL=postgresql+psycopg2://user:pass@host/db \
  python -m pytest tests/ -q               # PostgreSQL, ~5m15s

Run it on both. They are not interchangeable: SQLite ignores foreign keys by default and has no FOR UPDATE SKIP LOCKED, and both differences have hidden real bugs in this codebase already.

Note: run pytest tests/, not bare pytest — the backend root holds live-server scripts that pytest would try to collect and fail on.

2 · End-to-end against a running deployment — 45 checks

cd backend
PEOPLEOPSLAB_BASE_URL=https://payroll-saas-api-r6a8.onrender.com \
PEOPLEOPSLAB_PLATFORM_EMAIL=you@yourdomain.in \
PEOPLEOPSLAB_PLATFORM_PASSWORD='…' \
  python e2e_deployed.py

Production has no signup, so the runner signs in as platform staff from those two variables, creates a throwaway client workspace, accepts its invitation, signs in at /w/<workspace>/login, and checks the same credentials are refused at another workspace's address. Against a development stack with open signup it signs up instead (40 checks). The throwaway owner gets a fresh random password every run — it once had a fixed one written in the script, which on production would have been a live login with a published password. It then configures the workspace, uploads three months of master, attendance and registers, validates, reconciles a bank file, builds a JV and exports it to Tally. Exits non-zero if anything fails, so it works as a release gate. Safe against production — entity scoping keeps everything it creates inside its own organisation — but it writes, so don't aim it at a tenant whose audit trail you care about.

It asserts the single most important production setting: that an unauthenticated request is refused. A deployment that answers /api/org/entities without a token is serving payroll to the internet.

2b · Scale benchmark — 8,000 and 20,000 employees

cd backend
DATABASE_URL=postgresql://…/throwaway_db \
  python tools/benchmark_validation.py --sizes 8000 20000 --out bench.json

Generates synthetic registers with planted defects whose expected findings are computed independently of the engine, drives them through upload → queue → worker → paged reads → re-run → comparison, and reports each step's time, CPU and peak memory, plus storage per run. Exits non-zero unless every planted defect is found exactly. Use a throwaway database. Latest figures are in docs/BACKGROUND_JOBS.md §15.

If the site loads but nothing works, check BACKEND_URL first

This took the live site down on 25 September 2026. On a deployed host the browser calls /api/proxy/api/… and the Next.js server forwards to BACKEND_URL. With that variable unset the relay answers 502 proxy_misconfigured and never contacts the API at all.

The tell is in the metrics, not the page: the web service wakes repeatedly while the API never wakes at all. If people are visiting and the API has no instance and no logs, the request is dying at the relay.

Set it to the API's own URL — https://payroll-saas-api-r6a8.onrender.com, not a custom domain — on the web service. It is server-side only and must never be prefixed NEXT_PUBLIC_, which would publish it to every browser.
